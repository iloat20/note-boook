## 严重（必须修复）

### #1 `calcPosition` 在交易按日期降序时算错已实现盈亏 —— 明细页 / 记录页金额错误
- **链路**：
  - `utils/models/transactionIndex.js:33` — `getByStockId` 返回**按日期降序**的交易（`b.date > a.date ? 1 : ...`）。
  - `utils/services/positionService.js:28` — `calculatePosition` 把该数组**原样**传入 `calcPosition`。
  - `utils/helpers/positionCalculator.js:56` — FIFO 批次循环 `for (const t of transactions)`：BUY 入栈，SELL 消耗**数组中靠前**的批次。
- **后果**：降序下「先卖后买」，SELL 在对应 BUY 批次入栈前就被处理 → 无批次可匹配 → `matchedSellAmt = 0` → `realizedPnL` 塌缩为 **0**（实际应为 195 等）。
  - 实证（node 复现）：buy100@10 fee5 → sell100@12，升序喂入得 **195**，降序（生产真实路径）得 **0**；跨轮次买回再卖场景得 195 vs **45**。
- **影响面**：`packageDetail/pages/detail/detail.js:331` 与 `packageRecord/pages/record/record.js:142` 据此渲染 `realizedPnL / floatingPnL / avgCost / quantity` —— **用户看到的单股盈亏是错的**。首页多数能"侥幸"正确，是因为 `batchCalculatePositions` 走 `Transaction.getAll()` 的存储顺序（通常接近时间序），但该路径同样对顺序敏感。
- **修复**：在 `calcPosition`（及 `batchCalcPositions` 内部分组后）入口处按时间正序排序，使计算与调用方顺序无关：
  ```js
  transactions = [...transactions].sort(
    (a, b) => (a._sortKey ?? Date.parse(a.date)) - (b._sortKey ?? Date.parse(b.date))
  );
  ```
  （`_sortKey` 为数值毫秒，已在 entityFactory 中生成，排序更安全。）

## 重要（应当修复）

### #2 `getStrategyStats` 多标签交易重复计数
- **位置**：`utils/services/statsService.js:94-108`
- **问题**：每笔交易遍历 `t.strategies`，对**每个**标签都 `count++` 并累加**全额** `buyAmount / sellAmount`。一笔标记 `[A, B]` 的交易会让 A、B 的 `count` 各 +1（计的是关联数而非交易数），且 `netPnL`（= sellAmount - fees - buyAmount - fees）被**整笔计入每个标签** → 跨标签求和时该笔交易被算两次。
- **影响**：stats 页「策略统计」对任意多标签交易失真。
- **修复**：确定归因策略并一致应用，例如 (a) `count` 计不同交易（每个标签只 +1 且每笔交易只计一次），(b) 金额按 `1/nTags` 分摊或仅计入首个标签。

### #3 明细页「总盈亏」漏算分红，与 stats / 组合页不一致
- **位置**：`packageDetail/pages/detail/detail.js:346` — `const totalPnL = position.realizedPnL + position.floatingPnL;`（丢弃 `dividendIncome`）。
- **对照**：`positionCalculator.js:130` 与 `statsService.getTotalStats` 定义的 `totalPnL` **包含** `dividendIncome`。
- **影响**：同一只股票，明细页的「总盈亏」与 stats / 组合页数值不一致。若分红在别处单独展示可接受；否则应补 `position.dividendIncome`。

### #4 日期区间过滤：本地边界 vs UTC 排序键混用
- **位置**：`pages/stats/stats.js:198-200` 用**本地** `Date` 构造 `yearStart/yearEnd`，而 `getByDateRange` 比较的是 `_sortKey = new Date(t.date).getTime()`（`t.date` 为 ISO/UTC 字符串，`entityFactory.js:93`）。
- **影响**：跨年午夜或境外（UTC 时间差）交易可能被错误分到相邻年份，扭曲年度复盘的 `yearInflow / yearOutflow`。
- **修复**：边界改用 UTC（如 `new Date(Date.UTC(year,0,1))`）或把 `_sortKey` 换算成本地日毫秒再比较。
